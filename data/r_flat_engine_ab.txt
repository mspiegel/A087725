both *add state to hot structures* to get there — A grows AxisSlot by a byte, B

LANDED: D1.

D1. The packed-key update was two `key_get_cell` reads, two `key_set_cell`
writes, a `key_set_blank` and a branch. All of it collapses into ONE table read
plus one `wrapping_add`, because the 3-bit fields cannot carry into each other:
  - M[rf][g] >= 1 before the decrement, M[rt][g] <= W-1 before the increment
    (rt is the blank's line), and a 3-bit field holds 0..=7 — no borrow, no carry;
  - the blank field is the top field (bits 60-62, bit 63 unused), so its +rf-rt
    disturbs nothing above it;
  - g == W-1 is not encoded at all, so the cell part is zero — which also folds
    away the branch.
KEY_DELTA[rf][rt][g] is 5x5x5 u64 = 1000 B, L1-resident. Both D1 runs came in
below EVERY baseline run. The `pack` drift assertion pins the arithmetic against
the field-insert form on every node of the differential test.

D2 rejected. Writing the frame with h=0 and then overwriting h looked like a
redundant store plus a store-to-load round trip through row_at/col_at. It is not:
the measurement is flat (16.82 / 16.77 vs a 16.77-16.90 baseline), so LLVM was
already eliminating the dead store and forwarding the value. A reminder of §8i's
governing law — the profiler shows you where, but only removing real
multi-instruction work moves the needle, and this was not real work.

Tighter neighbour pre-prune — measured DEAD on R (2026-07-29)
=============================================================
child_h_lb is loose by exactly the changed axis's surcharge (lb = h - surch).
Instrumentation on R at exhaust-144:

  candidates   769,806,911
  pre-pruned   347,427,106   45.13%  (free array read; never counted as nodes)
  built        422,379,805   = nodes - 1
    over-bound 103,397,347   24.48% of built — materialised then discarded
    descended  318,982,458   75.52%

So ~10% of runtime goes into building children the search throws away one line
later. Closing the gap needs a lower bound on the child's surcharge WITHOUT the
probe. The child's demand is free (board-derived); its curves are not.

SCAN (examples/cwd_curve_floor.rs, over all 65,650,495 overlay states):

  PREMISE "a demanded line always costs >= 1 nibble": FALSE
  floor[line][demand] = min nibble over all states
      line 1 (top/left)      d=1..4 -> 1 2 3 4
      line 2,3,4 (interior)  d=1..4 -> 0 0 0 0
      line 5 (bottom/right)  d=1..4 -> 1 2 3 4
  Only 4.83% of (state,line,demand) triples have a zero nibble at all.

The outer-line floors ARE a sound, zero-memory rule: demand d on line 1 or 5 of
the changed axis => surcharge >= 2d. Counterfactual measurement on R:

  over-bound builds with ANY outer-line demand:  9,039  (0.01%)
  would-be caught by the floor rule:             9,028  (0.01%)

DEAD ON R, and structurally so — not bad luck. R is the 180 deg rotation, so its
outer lines hold no residents at all:
    R row 1 = [_, 24, 23, 22, 21]  -> residents: NONE (all belong to row 5)
    R row 5 = [ 5,  4,  3,  2,  1] -> residents: NONE (all belong to row 1)
    R row 3 = [15, 14, 13, 12, 11] -> ALL residents (row 3 maps to itself)
Every demand R carries sits on an interior line, which is exactly where the floor
is 0. The rule fires on 1 in 10,000 wasted builds. (When it does fire it works —
9028/9039 = 99.9% — it just never fires.)

VERDICT: both cheap routes are closed.
  - free +2 from "demand implies cost": premise false for interior lines.
  - outer-line floor: sound and free, but fires on 0.01% of R's wasted builds.
Only the exact per-state bound remains — store neighbour INDICES into a flat
index-addressed table (~3.3 GB, vs ~6.6 GB to copy neighbour curves). That also
eliminates the probe outright, and it sidesteps why the flat table was rejected
in PUZZLE24.md:406 (that rejection was about paying the contingency rank per
node; with neighbour indices you rank once, at the root). Est. ~10%, and it
retires node-identity as the A/B control since pre-pruned children are not
counted.


Index-addressed cWD table (neighbour edges) — measured REGRESSION, reverted (2026-07-29)
=========================================================================================
Idea: give each merged-table entry its neighbours' INDICES, so the search follows a
precomputed edge instead of hashing a packed key per child. Built in three stages,
each independently verified:

  stage 1  FlatTable: 65,650,495 states re-indexed. wd + curves co-located (12 B),
           neighbour edges in a parallel array (40 B). ~3.4 GB vs the ~1.2 GB hash.
           Verified EXHAUSTIVELY: every wd, every curves, all ~656 M edges land
           exactly where neighbor_keys() says.
  stage 2  Engine navigates by index. AxisSlot 32 B -> 12 B (u64 key + 10 B cached
           neighbour-WD array both deleted); KEY_DELTA and all packed-key arithmetic
           deleted; probe replaced by an edge follow. Node-identical by construction.
  stage 3  prepare/commit split: a child's h is computed in locals and the arena is
           written only on descent, so a rejected child costs 0 writes (was ~56 B).
           Also node-identical — the bound is unchanged, only the commit is deferred.

Node-identity gate passed on the final code (525 s in debug, 96 search pairs, all
drift assertions live). A/B on R at exhaust-144, sequential, alternating:

  D1   15.91 s  26.55 Mn/s        <- previous best (hash + KEY_DELTA)
  idx  16.29 s  25.93 Mn/s
  D1   15.74 s  26.83 Mn/s
  idx  16.48 s  25.62 Mn/s

  medians: D1 15.83 s, idx 16.39 s  ->  +3.5% SLOWER. No overlap between the sets.

WHY (the correction that matters). The ~10% estimate assumed the profiler's 4.6%
`probe` was mostly the HASH. It was not — it was the MEMORY ACCESS. Removing the
hash saved almost nothing, and edge navigation ADDED a second dependent access:

    before   hash(key) -> one lookup in a 1.2 GB table
    after    nbr[parent_idx] -> cell[child_idx]   two dependent loads, 3.4 GB resident

Two misses instead of one, over a table ~3x larger. That is the whole regression.

This independently re-derives PUZZLE24.md:406 and sharpens why it holds. That
rejection was read as "the per-node contingency rank cost more than the hash", which
suggested precomputed edges would sidestep it. They do not: for a 65.6 M-entry state
space the address computation was never the cost — the ACCESS is — and enlarging the
table to carry the edges makes it strictly worse. No indexing scheme fixes this.

Consequence for the tighter pre-prune: the exact-bound route is dead too, since it
required exactly this table (the child's curves reachable without a probe). Combined
with the curve-floor scan above, ALL routes to a tighter neighbour pre-prune are now
closed — free +2 (premise false), outer-line floor (fires on 0.01% of R), and the
exact per-state bound (its table is a net loss).

REVERTED. flat.rs is byte-identical to the D1 state; flat_table.rs deleted; the
cwd.rs/solve24.rs hooks undone. Sources kept for the record in the session scratchpad
as flat_idx_REGRESSION.rs / flat_table_REGRESSION.rs.

Still unmeasured: stage 3 (prepare/commit) in isolation. It is orthogonal to the table
redesign and can sit on the hash-based engine — worth ~56 B of avoided arena writes per
rejected child (24.48% of children), so plausibly 1-3%, i.e. possibly noise.


Register-resident frame fields — LANDED (2026-07-29)
=====================================================
Target: `run_flat`, the largest profile component (43% of the diagnostic sample).
`cand` and `minf` are the only fields of the current frame the loop MUTATES, and

arena unchanged and see identical values.

Hold the two in locals; refresh the arena copy only on descend and ascend:

    descend:  arena.hot[d].cand = cand; arena.hot[d].minf = minf;
              cand = <child's candidate set>; minf = u8::MAX;
    ascend:   cand = arena.hot[d].cand; minf = min(arena.hot[d].minf, sub);

distance in the abstract graph, so an edge moves it by at most one: every
neighbour is wd-1, wd, or wd+1. With "absent" that is exactly four codes — 2 bits
x 10 slots = 20 bits, so 3 bytes instead of 10. No scan needed; it is a theorem
about BFS distances, and set_nbr_wd debug-asserts the delta stays in -1..=1.

Probe cache — REGRESSION, reverted; and the corrected model (2026-07-29)
=========================================================================
Simulated a direct-mapped cache in front of the merged table (instrumentation
only, 422,379,805 probes on R at exhaust-144):

  1 K entries (32 KiB): 77.40%     16 K: 96.42%
  4 K entries         : 89.39%     64 K: 98.91%

That is TEMPORAL locality only. Spatial locality is absent by construction —
hashing scatters keys — so each distinct hot key costs its own cache line, and the
hot set spans 256-512 KiB of LINES while holding only ~120 KiB of data. The model
was: that puts it in L2, so compacting into a 32 KiB contiguous table converts L2
hits into L1 hits, worth ~5%.

Built it: 1 K entries, tag and cell interleaved (32 B, align 32) so a hit touches
one line. Node-identical by construction — a pure memo of an immutable table,
exact key match required.

  baseH  15.37 s  27.48 Mn/s
  H      16.34 s  25.86 Mn/s
  baseH  15.38 s  27.47 Mn/s
  H      16.18 s  26.10 Mn/s
  medians 15.375 vs 16.26  ->  +5.8% SLOWER. Reverted.

WHY, and the correction that matters. The compaction model predicted -5% and got
+5.8%. Two costs it ignored, both of which we had already learned about:
  - the tag test is a 77/23 branch, i.e. MISPREDICTING — and F had just shown a
    mispredicting branch here is worth ~4%. This added one back.
  - a miss writes 32 B; 97 M misses = ~3.1 GB of extra stores.
And the benefit it assumed (an L2->L1 upgrade) evidently was not there, meaning
the probes were already close to L1-resident.

THE MODEL, CORRECTED.  [*** SEE THE 2026-07-29 CORRECTION AT THE END OF THIS
FILE: every result below was measured at exhaust-144, where memory is NOT the
bottleneck; the counters show that changes at exhaust-146. ***]
Four memory-shaped interventions have now failed:
  shrink the entry (B)      time-neutral
  prefetch (§8i)            -0.7%, and -37% cross-child
  index-addressed table     -3.5%
  compact probe cache (H)   -5.8%
Back-end ("Instruction Processing") is 42.1% of the top-down breakdown, but every
attempt to attack it AS MEMORY has failed. The conclusion is that those stalls are
not memory stalls — they are dependency-chain and issue stalls, which Apple's
"processing" category also covers. That explains the whole pattern: the index
table lengthened a dependency chain, the cache added a branch and stores, and
shrinking or prefetching the table changed neither.

Every win in this engine has come from removing OPERATIONS, never from
rearranging memory:
  C   division-free demand keys       -4.8%
  D1  key update as one add           -2.7%
  A   register-resident cand/minf     -4.0%
  F   branchless demand predicate     -4.0%

================================================================================
Round: G1 / G2 / G3 — store-to-load round trips in the child's dependency chain
Date: 2026-07-29
Baseline: 2337d77 (flat engine with C + D1 + A + F)
Bench: solve24 --engine flat --heuristic cwd --prove-at-least 146 on R
       (exhaust-144, sequential, caffeinate -i). All runs node-identical.
================================================================================

Hypothesis. build_child passes three values through memory that were live in
registers a statement earlier, and arena.row / arena.col / arena.hot are three
separate boxed slices reached through one struct — the shape where field-level
noalias does not propagate and LLVM cannot forward the store:
  1. board copy+swap -> read `tile` back out of the copy
  2. AxisSlot store  -> h_at reads .wd/.surch back
  3. FrameHot store  -> loop reads .h back

G1 = fix (2) and (3): build_child returns h, built from cell.wd + surch + the
     untouched axis's term while all are in registers; FrameHot written once
     with the final h instead of h:0 then patched. Guarded by
     debug_assert_eq!(h, arena.h_at(d+1)).
G2 = fix (1): read tile off arena.board[d] before the copy. One line.
G3 = G2 + compute geom/tile once per candidate in the loop and pass to both
     child_lb and build_child (54.87% of candidates survive the pre-prune and
     reached build_child, which recomputed both).

NOTE: G3 CONTAINS G2 by construction — deduplicating the tile read means
build_child takes it from the caller, which reads it off the parent. G2 isolates
the reorder; G3 - G2 isolates the dedup. They are not orthogonal.

Results (search time, s; nodes = 422,379,806 in all 12 runs):

  base   15.12  15.01  15.00  15.01  15.02  14.99     mean 15.02   28.1 Mn/s
  G1     15.32  14.84                                 mean 15.08   +0.1%   REJECT
  G2     14.65  14.65                                 mean 14.65   -2.4%   
  G3     14.39  14.61                                 mean 14.50   -3.4%   KEEP

G1 REJECTED. Its two runs straddle the baseline — one above every base run, one
below every base run — with 0.48s of spread against the baseline's 0.13s. That
is no effect plus one disturbed run, not a small effect. LLVM was already
forwarding the tail stores, or the out-of-order core hid them behind the probe.

VERDICT, and the refinement to the model: the store-to-load round trip mattered
at the HEAD of the dependency chain, where `tile` gates the KEY_DELTA index and
therefore the probe, and NOT at the TAIL, where `h` feeds a branch the core can
speculate past. What stalls is the chain's start, not its end. This is the same
category as C/D1/A/F (remove work / shorten the chain) and NOT the category that
has failed four times (rearrange memory: shrink entry, prefetch, index table,
probe cache).

G3 - G2 = -1.0%, but G3's own two runs differ by 0.22s, so the dedup increment
sits inside its own spread. Not settled by four runs; G3 is the better binary
either way.

Cumulative for the flat engine on R at exhaust-144:
  recursive 21.83s (19.35 Mn/s) -> 14.50s (29.1 Mn/s) = -33% time, +50% thpt.

NOT TRIED, and why. The pre-prune's `f > bound` fires on 45.13% of 769,806,911
candidates — the worst-predicted branch left in the engine. It cannot go
branchless: it decides whether to do the work it exists to avoid.

Round: H1 — goal-coded board (store where a tile wants to go, not which it is)
Date: 2026-07-29
Baseline: 8fb4363 (flat engine after the recursive-engine deletion)
Bench: solve24 --position R --prove-at-least 146 (exhaust-144, sequential)
================================================================================

The board stored tile numbers, so the head of every node's dependency chain was

  geom -> tile = board[geom.from] -> g = GOAL_ROW[tile] -> KEY_DELTA[rf][rt][g]
       -> key -> fmix64 -> probe

with GOAL_ROW a dependent L1 load. But the engine never needs a tile's identity,
only its destination. Storing (goal_row << 4) | goal_col per cell makes `g` a
shift on a byte already in a register, deleting that load from the chain head —
the same lever G2 pulled for -2.4%.

Encoding is a bijection: tile t has goal cell t-1, and t-1 < 24 covers every
(row, col) except (4,4). Blank takes 0xFF.

Two effects, both confirmed rather than assumed:
  * GOAL_ROW and GOAL_COL became DEAD CONSTANTS and were deleted. That is the
    direct evidence the load is gone, not an inference from timing.
  * The demand predicate lost its `tile != 0` term. 0xFF's nibbles are both 0xF,
    which can never equal a line index g in 0..5, so the guard is structurally
    unnecessary — not merely optimised away.

Results (nodes = 422,379,806 in all four runs):

  base   14.12  14.13     mean 14.125   29.90 Mn/s
  H1     13.73  13.67     mean 13.700   30.83 Mn/s     -3.0%   KEEP

Both H1 runs below both base runs; baseline spread 0.01s, the tightest pairing
measured in this engine.

Cumulative on R at exhaust-144, unchanged nodes throughout:
  recursive 21.83s (19.35 Mn/s) -> 13.70s (30.83 Mn/s) = -37% time, +59% thpt.
  Landed: C, D1, A, F, G3, H1.

Round: widemul-fold hash — replace Murmur3 fmix64 on the probe path
Date: 2026-07-29
Baseline: 7511468 (flat engine with C, D1, A, F, G3, H1)
Bench: solve24 --position R --prove-at-least 146 (exhaust-144, sequential)
================================================================================

fmix64 (2 muls + 3 xor-shifts, strictly serial) sits directly between the packed
key and the probe address — the longest single segment on the node's critical
chain. walking_distance.rs recorded that FxHash had been rejected because a
single multiply "clusters them in hashbrown's low-bit buckets and probes blow
up", which looked like it closed the question. It does not: that failure is
DIRECTIONAL. A multiply propagates entropy upward, so low input bits reach high
product bits but never the reverse, and SwissTable indexes off the LOW bits.
Taking the HIGH half of a widening multiply and folding it down fixes exactly
that.

Settled by instrumentation before any timing run
(cwd.rs::probe_length_distribution_by_hash), modelling hashbrown placement over
all 65,650,495 merged-table keys at 49% load:

  hash                 mean hops     p99    max   displaced   ctrl max/mean
  fmix64 (current)        0.0003       0      2       0.03%       1.005
  single multiply        79.1746     325    581      98.72%       1.001
  fib + xorshift32        0.0221       1      5       1.97%       1.001
  fib + rot32             0.0195       1      6       1.73%       1.101
  widemul fold            0.0003       0      3       0.03%       1.001

The "single multiply" row REPRODUCES the documented blow-up, which is what
validates the model rather than leaving it a plausible simulation. widemul fold
places identically to fmix64 and spreads the control byte slightly better.

Distribution measured first, deliberately: a timing A/B alone conflates "hash got
cheaper" with "probes got longer", so a null result would not say which, and the
failure mode is a silent throughput cliff rather than anything that breaks.

Results (nodes = 422,379,806 in all four runs):

  base   13.69  13.71     mean 13.700   30.84 Mn/s
  wm     13.50  13.32     mean 13.410   31.50 Mn/s     -2.1%   KEEP

Both wm runs below both base runs; baseline spread 0.02s.

PREDICTION MISS, third of its kind. I estimated 4-7% from the latency argument
(fmix64 ~9-14 serial cycles vs ~5) and measured 2.1%. The isolated length of a
serial segment overstates its cost here: a node has up to three candidates whose
chains are independent, so the core overlaps them and shortening one recovers
less than its length. Same overshoot as the index table and the probe cache.
Treat isolated-latency arithmetic as an upper bound, not an estimate.

Cumulative on R at exhaust-144, unchanged nodes throughout:
  recursive 21.83s (19.35 Mn/s) -> 13.41s (31.50 Mn/s) = -39% time, +63% thpt.
  Landed: C, D1, A, F, G3, H1, widemul.

Motivated by a fresh hardware-counter run, the first since G3/H1/widemul landed.
Top-down, normalised (categories summed to 103.5% before scaling; ~11s window of
a 14.5s traced search; IPC 3.22):

                        post-F      now      delta
  useful / retiring      38.7%     37.2%     -1.5pp
  discarded / bad spec   15.8%     19.9%     +4.1pp
  back-end / processing  42.1%     42.9%     +0.8pp

Reading: G3/H1/widemul removed work, so cycles/node fell ~39% while the
mispredict penalty stayed fixed per bad branch — bad speculation therefore grew
as a *share*. That pointed at the pre-prune's `f > bound`, which fires on 45.13%
of 769,806,911 candidates (near-maximal entropy), ~3 branches per node.

H5 hoisted the pre-prune out of the inner loop into `prefilter`, evaluating it
for all candidates of a node at once and returning a survivor bitmask; the inner
loop then builds every candidate it pops. Accept/reject by csel, minf folded
branchlessly with u8::MAX as min's identity. No extra child_lb calls — it
already ran for every candidate. Node identity verified by the frozen oracle
(180 cases / 37M nodes, all green).

  base   13.42  13.42     mean 13.420   31.48 Mn/s
  H5     15.49  15.65     mean 15.570   27.13 Mn/s     +16.0%   REJECT

Baseline spread 0.00s, so the regression is unambiguous.

WHAT THIS COSTS THE MODEL. The counter share was real but the inference from it
was wrong: a large "discarded" share does NOT imply that removing the specific
high-entropy branch pays. Restructuring to remove it cost far more than the
mispredicts it saved. Candidate mechanisms, none yet measured: `prefilter` is
inlined at two sites and each carries its own loop, so the hot loop's register
allocation may have degraded and reintroduced the spills the flat engine exists
to avoid (§8l); and the per-candidate `lo = lo.min(...)` serialises a chain
across prefilter iterations that the old lazy path only touched on a prune.

Also folded in and now unmeasurable separately: H5 gave up G3's dedup half by
recomputing geom/tile for survivors. That was worth at most ~1% and cannot
explain 16%.

STANDING LESSON, now with two independent confirmations. Every intervention that
RESTRUCTURED the loop has lost (prefetch -37%, index table -3.5%, probe cache
-5.8%, H5 +16%); every one that REMOVED OPERATIONS from the chain head has won
(C, D1, A, F, G3, H1, widemul). Top-down counters are good at saying which
*category* is large; they are not evidence that a given restructuring will
capture it.

H5b — same idea with #[inline(always)]              *** ALSO REJECTED, +12.7% ***
--------------------------------------------------------------------------------

H5's autopsy was disassembly, not more benchmarking, and it found a concrete
defect: `#[inline]` is a hint and LLVM DECLINED it (652 B, two call sites, holds
a loop), so `flat_bounded` carried a real `bl ...prefilter...` — ~319M calls,
each spilling loop state across a `&mut Arena` boundary. H5 therefore never
tested the idea it was meant to test.

H5b forces `#[inline(always)]`. Verified in the disassembly BEFORE benchmarking
(pre-registered: an unverified binary would not be measured):

                    prefilter sym   bl prefilter   insns  sp_st  sp_ld  cond  csel
  baseline              absent            0         1196    49     69    102    26
  H5   (call)           present           2         1168    45     73     96    23
  H5b  (inlined)        absent            0         1360    50     97    122    40

Call gone — but stack RELOADS up 40% (69 -> 97), which is the register-pressure
mechanism I had originally guessed for H5 and which only materialises once the
loop is actually inlined at both sites.

  base   13.41  13.83     mean 13.620   31.03 Mn/s
  H5b    15.26  15.44     mean 15.350   27.52 Mn/s     +12.7%   REJECT

Removing the call recovered ~3pp of ~16pp. The rest is the restructuring itself.

VERDICT — this family is closed. The pre-prune's `f > bound` is the
highest-entropy branch in the engine (45.13% of 769,806,911 candidates) and
hoisting it out of the inner loop lost under TWO DIFFERENT implementations with
TWO DIFFERENT dominant costs (call overhead, then spill pressure). That is not
one experiment failing twice; it is two distinct costs each exceeding whatever
the mispredicts were worth. Conclusion: bad speculation's ~19.9% top-down share
is largely NOT recoverable here — the branches that mispredict are the ones
doing essential control flow, and any structure that defers or batches the
decision costs more than the misprediction does.

Do not re-litigate by trying a third shape (unrolled 4-way mask, SIMD compare,
sorted candidates) without new evidence that the *cost model* has changed.

METHOD NOTE, worth keeping. The disassembly diff cost ~1 minute and zero
benchmark runs, and it converted "H5 lost, mechanism unknown" into a specific
falsifiable retry. The two A/Bs cost ~6 minutes. Disassembly first.

================================================================================
CORRECTION (2026-07-29): every A/B in this file ran at exhaust-144, and the
memory-shaped conclusions do NOT generalise to deeper thresholds
================================================================================

This file repeatedly states, in increasingly confident form, that "memory-shaped
interventions have all failed" and that back-end stalls here are therefore
dependency-chain stalls rather than memory stalls. That conclusion is sound *for
exhaust-144*. It was then quoted as a property of the engine. It is not.

Every A/B recorded above — B, prefetch, index table, probe cache, G1/G2/G3, H1,
widemul, H5, H5b — was run at exhaust-144 on R.

Counter profiles of both thresholds, same process, same session, same power
state, show the regime changes with depth:

                             exhaust-144   exhaust-146
  IPC                             3.25         2.76      -15%
  useful / retiring              37.5%        35.7%      -1.8pp
  discarded / bad speculation    22.2%        22.3%      +0.1pp
  back-end / processing          40.3%        42.0%      +1.7pp

  (normalised; raw category sums were 107.0% and 93.4%, so read the split as
   directional. IPC is the robust figure and matches the independently measured
   throughput drop of -17.7% within the same run: 30.63 -> 25.22 Mn/s.)

Work per node is identical at both thresholds, so the only way throughput falls
is more cycles per node — ~21% more — and the counters put the increase in the
back-end, with bad speculation flat to a tenth of a point. The mechanism is
locality: a deeper threshold walks a larger slice of the 4.43 GB merged map.

WHY THIS MATTERS FOR THE REJECTS. The prefetch entry's recorded reason for
failing is "working set already resident; nothing to hide". That is a statement
about exhaust-144, and it is exactly the condition the counters show breaking at
146. So the strongest of the memory-shaped rejects is untested in the regime
where its premise would hold. Entry-shrinking is the other one worth revisiting,
since a smaller entry touches fewer lines and pages — a locality fix rather than
a latency-hiding one. A probe cache is the weakest re-test: it needs reuse, and
reuse is what is degrading.

WHAT IS NOT AFFECTED. The seven wins (C, D1, A, F, G3, H1, widemul) removed work
from the node's dependency chain; that work is removed at every depth, so they
carry over. H5/H5b's rejection also stands on its own mechanism (a non-inlined
call, then spill pressure), independent of depth.

COST OF THE RE-TEST, so nobody starts it casually. An exhaust-146 A/B is ~12 min
per run. On battery, two runs of identical work differed by 2.9% and the session
spanned ~10%, so resolving a few-percent effect needs 4+ runs per arm: ~1.5 h per
A/B. R's thresholds are parity-quantised (144, 146, 148), so there is no cheaper
intermediate depth on this board to use as a proxy.

The prize is correspondingly larger than anything left at 144: the gap between
the two regimes is 17.7%, and exhaust-146+ is the regime the R proof actually
runs in.
