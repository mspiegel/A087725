E1 (by code inspection — decisive without a bench)
--------------------------------------------------
The zbins are 1-bit DIFFERENTIAL tables: absolute values exist only via
ZPatternDb::cold_lookup, which descends the abstract graph one step per unit of
h — O(h) ranks+probes, tens of us for k8-scale h. So a from-scratch consult
design is dead on arrival (this is §8u's retraction, sharpened), and no value
cache can rescue it (a miss costs us). The only viable design is incremental:
maintain (ProjectedState, h) per group per view, diff_lookup O(1) on cost-1
edges. Design A' (flat): consult = advance-by-one-move from the parent's slot,
done ONLY for children that pass cWD's f-test. Every entered node has a current
slot, so there is NEVER a catch-up — the entire recursive LazyMaxInc deferral
machinery (8% of samples, §8l) dissolves into the arena invariant.

-------------------------------

cWD-survivors, h = max(sum normal, sum reflected), both drivers.

Memo-cache sizing measurement (k8-probe-locality feature, 2026-07-30)
---------------------------------------------------------------------
Method: mirror of the cWD probe-cache sizing, but simulating the candidate
structure ITSELF — an (idx -> h) direct-mapped memo, key = idx*3+table, same
multiply-shift index as ProbeCache — online during a budgeted sequential run
(--zpdb8 --max-nodes 1.8B: all of 144 plus ~1.5B nodes of the 146 pass; ~9% of
the stream is the 144 regime). Hooked at k8_child's two diff_lookup sites; seed
cold_lookups excluded. An (idx -> h) hit is sound path-independently because
diff_lookup's old_h argument only disambiguates the 1-bit encoding — h is a
function of idx alone. NOTE: the memo key is idx, which is computed by rank —
so a hit skips the TABLE TOUCH only, not the rank.

  probes: 2,776,598,476 (1.55/node; tables a/b/c 36%/31%/33%)
  distinct 16 KiB pages: a 2.86 GB, b 2.26 GB, c 3.78 GB = 8.9 GB in one slice

  bits  /worker   hit      misses/node
  14    128 KB    63.76%   0.56
  16    512 KB    73.49%   0.41
  18      2 MB    81.29%   0.29     (cWD probe cache at ~this size: 98.6%)
  20      8 MB    87.31%   0.20
  22     32 MB    91.87%   0.13
  24    128 MB    95.14%   0.075

Findings:
1. Cacheable, but 20x weaker locality than cWD's stream (0.29 vs 0.0141
   misses/node at 18 bits). The aggregate ~2000x reuse is spread thin.
2. NO KNEE: ~5pp per 4x of size to 128 MB. Sizing is a budget call; 20-22 bits
   is the sensible range (64-256 MB total at W=8, noise next to 32.8 GB of
   tables).
3. The 8.9 GB page set in one slice confirms E4: the k8 working set can never
   be resident (~14 GB of RAM left after cWD + OS), so memo misses keep paying
   refault-class costs. No residency tuning escapes this.

Estimated lever value: ~20-30 ns/node (~a quarter of the k8 layer) at 87-92%
hit — enough to flip the 0.05% tie at 148, far short of the cWD cache's win.
Not built yet; the A/B cycle is ~40 min (memo in k8_child, regate 269,180,917 /
8,539,130,554, race 146 W=8).

Extended memo sizing: miss decomposition (2026-07-30, same 1.8B-node slice)
---------------------------------------------------------------------------
  distinct idx (HLL +/-0.8%): 58,788,203  -> mean reuse 47.2x, compulsory
  floor 2.117%. The working set is ~470 MB at 8 B/slot — reuse is HIGH but the
  live key set dwarfs any practical cache. (Prediction check: the "locally
  novel stream / single-digit reuse" hypothesis was WRONG; recorded so the
  reasoning isn't reused.)

  Associativity at equal capacity (LRU-in-set):
    2 MB:  dm 81.29 / 2-way 83.24 / 4-way 84.04
    32 MB: dm 91.87 / 2-way 93.04 / 4-way 93.50
  -> conflicts are +1.2-2.8pp; the misses are CAPACITY. Only size helps, and
  the flat ~5pp/4x slope is a skewed reuse tail: 1M slots (1.8% of the working
  set) already catch 87%.

  Per-table dm@20: a 90.09%, b 96.19%, c 86.51% — group c both recurs least
  and touches the most pages (3.78 GB): the workload scrambles c's tiles most.

  Warm-up: window hit rates flat from the first 512M probes
  (87.4/88.0/86.3/87.3/87.6) — sustained steady state, no cold-start artifact.

Design consequences:
  1. Key the memo by PACKED POSITIONS, not idx: bijective with idx (perfect
     ranking) so these hit rates transfer, and a hit then skips the rank AND
     the table touch — roughly doubling the lever (~40-50 ns/node of the 82 ns
     layer). That is enough to turn the measured 148 tie into a clear win.
  2. Direct-mapped, 22 bits (32 MB/worker), no associativity (capacity-bound).
  3. Caveat: sequential-stream rates are OPTIMISTIC for W=8 private caches —
     cross-subtree transposition reuse fragments across workers; expect high
     80s, not 92, per worker.

Positions-keyed memo cache — REJECTED at every size (2026-07-30)
----------------------------------------------------------------
Built as sized: direct-mapped (packed 8 positions + blank cell + table) -> h,
per arena, hits skipping BOTH rank and diff_lookup. Node-identical at every
size (269,180,917 / 8,539,130,554). Real hit rate 89.451% at 22 bits — only
2.4pp under the idx-keyed sim, so the blank-fineness cost was minor and the
sim's cacheability verdict was correct. And yet, W=8 exhaust-146:

  none (v2)   133.65 s          <- stands
  2 MB        138.44 s  +3.6%
  8 MB        148.69 s  +11.3%
  32 MB       151.4-155.7 s  +13-16%

MECHANISM (not a parameter): a memo must be cheaper to consult than what it
memoizes. The consult's average probe is ~25 ns — rank is the tight cache-hot
loop §8i measured (no cycle win from shaving), diff_lookup's HOT page subset
stays resident (1.8% of recursive samples) — while a random 8-B read into even
a 2 MB array costs comparable-or-more, and at 32 MB adds its own TLB misses
(2048 pages/worker vs ~3000-entry L2 TLB) plus 256 MB of RAM pressure evicting
table pages. The expensive table touches are the non-resident TAIL, and a
front-cache cannot pay only on the tail — it pays on every probe.

The reusable law, third form: sample share != reclaimable time (§8i);
LRU-model hits != direct-mapped hits (probe-cache-stats note); and now
HIT RATE != SAVINGS. The sizing measurement answered "would it hit" (yes,
89%) — only the A/B could answer "does a hit save more than the probe costs"
(no). Reverted to v2's direct rank+diff path; the k8-probe-locality
instrumentation and this record are kept.

Readahead-value measurement — madvise lever CLOSED without a clean A/B (2026-07-30)
-----------------------------------------------------------------------------------
Count-based (load-immune, valid on the contended box): on the page-event stream
(consecutive same-page probes collapsed — only 1.3% collapse, i.e. 98.7% of
probes change page), classify page faults at several eviction horizons and ask
whether a recent prior fault lies within a readahead window (±4/±8 pages, same
table), with a distance histogram.

  horizon      faults      cov+-4   cov+-8   D=1 | 2-4 | 5-8 | 9-64 | far
    50000   280,610,635   16.18%   23.83%   7.9 | 8.2 | 7.6 | 31.9 | 44.3
   200000   143,900,484   14.30%   21.25%   6.9 | 7.4 | 6.9 | 30.7 | 48.0
  1000000    57,900,411   12.50%   18.76%   5.9 | 6.6 | 6.3 | 29.2 | 52.1
  first-touch    542,956    8.67%   13.55%   4.1 | 4.6 | 4.9 | 25.1 | 61.4

Findings:
1. MADV_RANDOM's premise ("readahead is pure pollution") is WRONG: an 8-page
   cluster would absorb ~21% of faults, and the largest locality bucket is
   D=9-64 pages (~31%) — diffuse neighborhood reuse a ramping readahead can
   partially capture. Best case for the hint is gone; verdict
   neutral-to-slightly-harmful; the lever is CLOSED and does not earn an
   idle-box A/B slot. (Weak independent support for the direction of the
   contaminated afternoon regression.)
2. The trade readahead actually makes here: ~21% fewer fault stalls at ~equal
   SSD cost per fill, against ~6x page-cache churn (8 pages/fault vs 1) on a
   RAM-bound box. The counts can bracket but not settle that trade — kernel
   policy (cluster size, ramping) is unobservable — which is exactly why the
   verdict is "no clear upside" rather than a number.
3. CORRECTION to the mechanism story recorded with the madvise revert: 98.7%
   of probes change page, so there is almost NO adjacent-probe page locality
   from the cohort layout. The 87% memo-sim hit rates are TEMPORAL reuse at
   long distance; the spatial component lives at D<=64 pages across faults,
   not between consecutive probes.

Method note: this is the measurement that should have PRECEDED the madvise
edit, exactly as the sizing sim preceded the memo build — it costs one
budgeted run, is valid under load, and would have prevented a wasted A/B and
the contamination mess. Ahead-of-time pattern measurement now demonstrated on
both cache-shaped levers.

Two soundness bugs the node counts caught on the way (both mine):
1. `parent-1` on a cache miss is NOT usable to skip probes. diff_lookup is
   an exact reconstruction that selects parent±1 by the child's stored bit;
   given a parent 1 low it can return 1 HIGH (true parent 5, true child 4,
   degraded parent 4 -> 5). Measured as over-pruning: 184,461,339 nodes at
   exhaust-144 against the correct 205,119,447. The parity argument about
   lost prunes was fine; the flaw was assuming the codec tolerates an
   inexact base. Skipping probes also starves the cache of exact values.
2. The ranked miss path ranks a *board*, so the reflected σ-view must rank
   the REFLECTED board; passing the normal board to both views gave
   27,258,040 nodes. Fixed; both variants now node-identical at 205,119,447.

consult cost ~15% before the peek/store split.

subtrees of the same tree, so their probe streams overlap and eight private

User's insight: a cache KEY need not be a compact array index, only unique and
cheap. k8 can have no positional map (25^9 = 480 GB) but CAN have a

(`key ^= (src ^ dst) << 5·slot`). The 8-tile rank walk and the 32.8 GB mmap
then run only on a miss.

CONSULTING LESS OFTEN IS NOT AVAILABLE TO k8 (user caught this, 2026-08-02).
The k8 consult fires on 87% of counted nodes (6,779,472,719 consults against
7,802,326,121 nodes @146) and ~83% of its per-consult cost is paid whether or
not the cache hits, so gating looked like the one lever with real leverage —
and skipping a consult is admissible in the usual sense (it forgoes a prune,
never invents one).
It is NOT admissible here, because the zPDB is differentially encoded: one bit
per state (bit 1 of the distance), reconstructed as
`diff_lookup(child_index, h(parent))`. The value exists only relative to the
parent's, so k8_child maintains a CHAIN. Skipping a consult leaves that
depth's arena slot holding a previously-traversed sibling's data, and the next
reconstruction from it can read HIGHER than the truth — over-pruning, which
would silently invalidate a proof. A slack gate was implemented and reverted
before any number was taken from it.
The trade is structural: the 1-bit encoding that makes 30.5 GB affordable is
exactly what forbids skipping consults. Absolute-valued tables would allow
gating but cost 8x the space (k8 at u8 is ~80 GB per pattern — out of the
question); the LM family is unaffected, since its tables store absolute values
and its consults are independent.
Corollary: of the four gating ideas (slack, depth band, single σ-view,
blank-position), only SINGLE σ-VIEW survives — it drops one of the two chains
entirely rather than interrupting either, so it stays sound. Measured for k6
it kept 75% of the tier's unique reach for half the probes; for k8 the
σ-asymmetric partition makes the second view worth more, so the loss would be
larger. Unmeasured.

LOCALITY-PRESERVING RANK: closed by the move-frequency measurement.
Both the ranked layout (last factorial digit) and a positional one (lowest
digit) give near-neighbour addressing to exactly ONE tile per pattern; the
other seven move high-order digits and land far away — which is why the
measured consecutive-probe same-line rate was 0.12%. Density and locality
are in tension: dense indexing must be combinatorial (scatters neighbours),
local indexing must be positional (25^9 = 480 GB for k8, impossible). The
only free lever was choosing WHICH tile gets the fast digit, by move
frequency.
Measured @144 (110,013,419 consults):
  group a (40.2% of moves): 14.7 14.3 14.1 12.8 12.1 11.8 10.2 10.0 %
  group b (24.7%):          16.5 15.3 14.7 13.9 13.9 13.5  8.7  3.6 %
  group c (35.2%):          16.5 15.2 15.1 13.3 11.9 11.6  9.7  6.6 %
Uniform is 12.5%; the busiest tile carries 16.5%, i.e. 1.3x uniform. Digit
reordering would lift locality coverage from 12.5% to 16.5% of a group's
consults — 4 points — against a miss path that is only ~17% of the tier's
cost. Below noise. Structural reason: the search moves whatever neighbours
the blank, and the blank roams, so no tile in an 8-tile pattern can dominate.
Incidental: tile 20 takes just 3.6% of group b's moves, the lowest of any
tile — independent corroboration that the endgame cast (LM2's tracked tiles)
stays quiet until the very end.

SURPLUS-CODING GATE (absolute-value re-encoding of k8) — PASSES on quality.
Idea: store surplus = h - MD_sum(pattern's own tiles) instead of a 1-bit
differential. Both terms move by +/-1 on a cost-1 move, so surplus is EVEN and
0 at goal; b bits hold surplus/2. Clamping DOWN stays admissible. If it fits,
lookups become INDEPENDENT — which revives every idea the differential chain
killed (consult gating, depth gating that keeps its prunes, batch/epoch
evaluation, sorted sequential table access).

  surplus  0  254,995,221  38.63%   cum  38.63%
  surplus  2  241,759,190  36.62%   cum  75.25%

  surplus  6    9,384,073   1.42%   cum  99.96%
  surplus  8      260,170   0.04%   cum 100.00%
  surplus 10          137   ~0%     max observed

COST-PARTITIONED cWD (+) k8 — the tractable formulations collapse to max.
PhO (post-hoc optimization) assigns one weight per abstraction:
  maximise x*R + y*C + sum_g z_g*V_g   s.t. every operator's weights sum <= 1.
Operator supports: WD_row charges ALL vertical moves, WD_col ALL horizontal,
k8 group g charges moves of ITS tiles in BOTH directions. So each group faces
x + z_g <= 1 and y + z_g <= 1, hence z_g <= 1 - max(x,y), and with S = sum V_g
the objective reduces to x*(R+C) + (1-x)*S — linear in x, optimal at an
endpoint: max(cWD, k8), which the cascade already computes. Saturated cost
partitioning collapses the same way in EITHER order, because k8's three groups
cover all 24 tiles and leave zero residual for whatever saturates second.
Structural reason: cost partitioning pays when abstractions charge DIFFERENT
operators. Here cWD charges every operator (split by direction) and k8 charges
every operator (split by tile) — complete overlap, nothing to redistribute.
Measured (cost_partition_headroom, 576 boards, every 6th of survivors_148):
  mean cWD 111.4 (row 55.3 + col 56.1) | mean k8 110.4 | mean max 111.9
  k8 > cWD on 103 boards (17.9%)
  PhO/SCP LP BEATS max on 0 boards        <- collapse confirmed empirically
  k8's single largest group carries 37.6% of its value
  histogram (k8 - cWD): -8:1 -6:16 -4:111 -2:169 0:176 +2:75 +4:21 +6:5 +8:2
HEADROOM IS THIN: the two heuristics sit within ~1 unit on average and 91% of
boards fall in [-4,+2]. They measure nearly the same work by different routes.
NOT ruled out: per-OPERATOR cost partitioning, which needs a WD variant where
one group's tiles move free. The bar is computable from the above — giving
group g full cost yields V_g + cWD_-g, and with V_g ~ 41.5 (37.6% of 110.4),
beating 111.9 needs cWD_-g > 70.4, i.e. cWD must RETAIN 63% OF ITS VALUE WITH
8 OF 24 TILES MOVING FREE. Expect that to fail: WD charges for the blank

DFA / INVERSE-MOVE RESTRICTIONS AS A HEURISTIC PENALTY — closed by parity.
The move restrictions change the search graph, so the quantity to bound is the
RESTRICTED distance d_q(s) >= d(s); bounding it is admissible because the DFA
preserves an optimal root solution. The canonical exploit is one-step
lookahead:  h'(s,q) = max( h(s), 1 + min over DFA-legal children c of h(c) ),
which exceeds h(s) exactly when the restriction removed the child the
heuristic was counting on.
Measured @144 (counter over expanded nodes; pre-pruned children need no h,
since the parent survived => h_p <= bound-d, and the pre-prune fired because
lb > bound-d-1, hence lb >= h_p and they cannot lower the min):
  cWD-only  90,479,322 of 318,974,854 expanded (28.366%) fire
            gain +2 on 31,379,182; all-children-pre-pruned on 59,100,140
  cascade   19,355,708 of 102,793,625 expanded (18.830%) fire
            gain +2 on 12,073,542; all-children-pre-pruned on 7,282,166
THE GAIN IS ALWAYS EXACTLY +2, never more — forced by parity. h flips parity
every move, so a child is h_p +/- 1; "every child >= h_p" therefore means every
child is exactly h_p + 1, giving h' = h_p + 2. Buckets >= 4 are empty, as
predicted.
And +2 is precisely what IDA* already extracts. At 144 every node is slack 0,
so h_p = need; children with h_c >= h_p give f_c >= bound+1 and the ordinary
f-test prunes all of them. The lookahead would raise h(s) only AFTER computing
the children whose own f-test already did the work.
To add anything the lookahead needs gain > slack, so a slack-2 node needs +4,
which one step provably cannot produce. Two-step lookahead could reach +4 but
requires expanding grandchildren — which IDA* again does implicitly one level
deeper. The whole family reduces to what the min_next fold already collects.
Note the contrast with LM/LM2, which ARE this idea applied to the FINAL move
(the blank must enter cell 24 last) and pay 1.5x: the endgame is where the
move-ordering facts are unconditional and not already priced by the f-test.
